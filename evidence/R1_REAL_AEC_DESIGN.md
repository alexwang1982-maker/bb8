# BB-8 真实 AEC 协议级技术方案（仅设计，不在 R1 实现）

R1 明确禁止在 WebSocket 侧实现「伪 AEC」。本文件只提交设备侧/协议级的技术方案，供独立阶段评审；本轮不修改任何 AEC 相关代码行为（`client_aec` 默认 false，WebSocket 路径不调用 `_apply_aec`）。

## 1. 为什么 R1 不做服务端伪 AEC

- WebSocket 音频帧没有设备侧参考信号（render reference），也没有可靠的播放时间戳；服务端无法把「自己刚发出的 TTS」从麦克风信号里减去。
- 现有 MQTT 路径的 `_apply_aec(timestamp, frame)` 依赖 `timestamp>0` 与服务端保存的播放参考，但生产日志 `aec:false` 24 次、`aec:true` 0 次、`[AEC]` 0 次，说明该能力从未真实生效。
- 用「播放态静音/丢弃全部输入」代替 AEC 会违反「不得把所有播放期间音频一概丢弃」；R1 因此采用来源门控 + barge-in 专用队列，而不是伪造消除。

## 2. 真实 AEC 的必要条件

真实回声消除必须同时具备以下三项，缺一不可：

1. **参考信号**：设备端把正在播放的 TTS PCM（或明确的播放 sequence 标识）作为 reference 送给 AEC。
2. **时间对齐**：参考信号与麦克风采集共享时钟或有可校准的 timestamp，使 AEC 能对齐远端信号。
3. **因果顺序**：AEC 在拾音链路的最前端执行，输出才是「纯用户声」，再进入 VAD/ASR。

三者都在设备侧或协议层，无法由服务端 WebSocket 文本/音频消息单独推断。

## 3. 协议级方案（建议）

### 3.1 设备侧回声消除（推荐）

```
TTS 解码 → 扬声器播放
          └── 同时送入设备 AEC 的 reference 输入
麦克风 → AEC(reference) → 纯净用户 PCM → Opus → WebSocket/MQTT → 服务端
```

- 设备固件在播放 TTS 时把同一 PCM 流复制给 AEC reference。
- 服务端收到的已经是消除后的用户声，R1 的来源门控仍然保留作为纵深防御。
- 需要固件/ESP32 侧改动，不在本仓库范围，需单独排期与真机测试。

### 3.2 服务端 AEC（仅在协议补齐后可行）

若必须在服务端做，需扩展协议：

1. 设备为每帧音频携带 `capture_timestamp` 与 `playback_sequence`。
2. 服务端保存最近 N 秒的 TTS PCM，按 `playback_sequence` 对齐。
3. 服务端只对「有有效 reference + timestamp 的帧」执行 AEC；其余帧按 R1 门控处理，不得猜测消除。
4. AEC 结果才允许进入正常 ASR 队列。

当前 WebSocket 协议无上述字段，因此该路径在 R1 不可实施。

## 4. 验收要求（后续阶段）

- 真实声学插话测试：设备外放 TTS，真人从麦克风插话，验证 TTS 自声不触发 ASR、真人插话能打断。
- 预录音频连接真实 WebSocket **不等同真人声学测试**，只能作为协议链路回归。
- 必须记录 AEC 生效计数（当前生产为 0），并要求 `aec:true` 与 `[AEC]` 日志真实出现。
- 未满足以上条件前，不得宣称「AEC 已修复」或把伪 AEC 部署到生产。

## 5. R1 与本方案的关系

R1 用来源门控把「播放态帧」隔离到 barge 队列，保证即使没有 AEC 也不会把 TTS 自声当用户指令；这是**隔离**而非**消除**。真实 AEC 是后续独立阶段，二者不冲突、可叠加。
